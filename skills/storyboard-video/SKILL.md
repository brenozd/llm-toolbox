# storyboard-video

Honest promo video from the code. The MCP mounts only the current directory read-only at `/repo`.
Burns captions, renders 16:9 or 9:16 (`.srt` alongside) and can add an offline voice-over (Pocket TTS, `pt-BR` or `en`). No stock footage. Network: the `storyboard-video` entry has a network (web capture needs it, restricted by the tools to `localhost` / `host.docker.internal`); the `storyboard-video-exec` entry runs `--network none`.

## Rules
- All text (scenes, captions, narration) is in `spec.lang`; keep code, commands and identifiers verbatim. Never mix languages in one video.
- Never claim what you did not capture or cite. Numbers on screen need `scene.evidence = "file:line"`; the `uncited_stat` lint only sees a number *with* a unit (`40%`, `1.2x`, `8ms`, `5k`), so a bare integer (`42`, `2024`) is yours to cite by hand.
- Never open `.env`, keys or real user data; the MCP refuses them. Do not edit the repo.
- Never put in the video: container paths (`/work`, `/repo`, `/tmp`), meta lines about the making ("compiled in the container", "every number came from that run", "nothing typed by hand"), a claim the footage contradicts (typed heredoc vs "nothing typed"), filler outros, tool internals nobody asked about. Put in: what the product does for the viewer, one concrete before/after, real command output, repo-relative `file:line`. Hide setup noise with `capture_terminal_session(setup=...)` (PATH, cd, aliases; runs before the grab), so the viewer sees `mint_loader ./leak`, not absolute paths.
- Ask before: running repo code (exec), anything that needs a build. Tell the user the exact command.
- **Mutation policy.** Before any write action on the target (block an IP, quarantine, delete) ask the user explicitly and state what you will do. Use reserved test data only (`203.0.113.x`, `example.com`, `test@example.invalid`), reset the state before **every** take, then poll it until it is really back to baseline (a remove/`DELETE` API can answer ok while the state lags) and report the final state in the message, not just the command.
- **Remote target over ssh:** record with the [`screencapture`](../screencapture/) skill **on the host** — the `-exec` container has no network — and copy the file into the work volume; `capture_web` has to go to the non-`exec` entry; extracting from the volume across an arm64/amd64 mismatch needs `docker run --platform`. List the screencapture host deps in one preflight line before the first recording, so `sudo` is asked once: `xdotool`, util-linux `script`, `xterm`, `Xvfb`, `ffmpeg`, `Pillow`.
- **Measured, not remembered.** A duration or state taken from earlier context or from a summary is unverified: re-measure it (`render_status` → `elapsed_s`) before stating it, and never count the time you spent sleeping or waiting as elapsed work.

## Flow
1. `preflight`. Fix anything red. CLI/GUI need the `storyboard-video-exec` entry (`capture_terminal`, `capture_terminal_session`, `capture_gui`); web needs `storyboard-video`. Start Claude Code **from the repo root**: the entry mounts `${PWD}`, the launcher's working directory, as `/repo` — launched from `$HOME` or an IDE, `/repo` is the wrong tree.
2. `scan_repo` → kind guess (web|cli|gui), the candidate features (README sections, CLI flags, modules) and the README's language. `brand_tokens` for the theme.
3. **Brief (mandatory, stop here, before any spec).** Summarize first what `scan_repo`, the README and the code reveal. The client's words come from the repo — README sections and CHANGELOG (issues and commit messages are out of reach: `.git` is denied, so ask the user for those), read with `scan_repo`/`extract_code` and quoted with `evidence` (`file:line`) — so a field with no source is a **question**, never a default. Then ask, 5 content + 3 config (`ask_user_question`, or plain questions if it is unavailable):
   - (1) who watches it, and in what situation; (2) the pain in one sentence, **in their words**; (3) the one thing they do afterwards — a single CTA; (4) the single message the video must leave, **which screen/feature is the star** and what must be on screen in it; (5) **where it plays**: `hero` (site header), `ad` (paid, 15–30 s), `deck` (inside a pitch, often muted), `booth` (loop on a convention TV, read with no audio), `walkthrough` (2–3 min) — this sets the duration and whether it has to work muted;
   - (6) **aspect** (16:9, 9:16 or both — 3:4 is not supported yet), **language** of captions and narration (default the README's; pt-BR or en for TTS) and the **voice** when narration is on; (7) **music**: none (the default) or a **vibe** — ambient / calm / tech / epic / playful / elegant (see **Music**); no match means a silent video, and you say "no results" plus the reason rather than pick a track by hand; (8) **palette + tone** anchored to a reference: a hex set the user already uses, or "derive from the app" (= `brand_tokens`' theme and `provenance`, never a colour you invented unannounced), tone against a video they like or one they would swipe away.
   Record `/work/brief.md`, and the same as `direction.brief = {audience, pain, promise, cta, placement}` (`validate_spec` type-checks it as of Fase 1; on an older server it is the session's own brief, and `placement` drives `direction.purpose`: ad→sales-video, hero/walkthrough→feature-demo, booth→booth-loop, anything else (deck…)→other; and `direction.arc`: ad, hero, walkthrough, booth→booth-loop, deck→none, which only warns `arc_unknown`).
3b. **Directing (before the script: the look is decided here).** Be the video's director, in this session (host, with network) — never inside the MCP container: read `brief.md` + `scan_repo` + `brand_tokens` + the captures you plan, run 2–4 web searches on how that format is cut *now* ("booth loop signage", "product demo video structure", "sales video value beats"), then write `/work/direction.md`: purpose, audience, tone, palette and where it came from, the cited research (URL + the one thing you take from it), the per-scene plan and `must_avoid`. Search offline or empty → the built-in per-format defaults with `research: []`, never a blocked pipeline. The same content goes into `spec.direction` (see **Spec**), and the plan is yours to keep current: a Fase-2 rough cut or a `reframe` edits `direction.scenes` in the same step (`validate_spec` only warns when a scene is missing from it).
3c. **Arco + hooks (gate 1 — one message, then stop).** Take the arc template from `placement`; the beats are the `role` enum and the percentages are a starting point, never a rule (`implication` — what the problem costs — goes between `problem` and `reveal` when the stakes are the hook; `result` — the measured outcome — replaces `proof` when a number closes the video):
   - `ad` / loop, 15–30 s: hook 15 · problem 20 · reveal 35 · proof 15 · cta 15. `booth` loop: the same arc, readable with no audio.
   - `hero` / feature demo, 45–90 s: hook 12 · problem 20 · reveal 10 · value (one whole workflow) 40 · proof 10 · cta 8.
   - `walkthrough`, 2–3 min: the same, with `value` as 2–3 beats.
   In that one message present: **2 one-line arcs** plus a logline, and 5–10 **hook** candidates from the archetypes (curiosity gap, falsifiable claim, specific proof, pattern interrupt, stakes) narrowed to 2 finalists with their first frame described. The user picks arc + hook. A hook whose promise has no later `proof`/`value` scene is a rewrite, not a shot. No answer, no script.
4. **AV script (gate 2 — stop here).** Two columns, one row per scene: **audio** = the exact words to be spoken | **visual** = shot, on-screen text and the `file:line`/capture that backs it — with the accumulated time at **2.5 words/s** and a `[beat]` marker per scene. It replaces the scene table, and every number and piece of on-screen text appears exactly as it will be typed. Recommend a feature subset from the `scan_repo` candidates with a one-line reason each; 5–7 scenes, 30–45 s, unless the placement says otherwise. `[beat]` may stay in `scene.narration`: the voice never reads it, `narrate` turns it into a 0.45 s breath of low-level room tone and the captions drop it. Wait for approval.
4b. **Script review (mandatory, before `narrate` and before the stills are final).** Three read-only lenses, each in a fresh-context subagent (with none available, say so in the message and re-read the script once per lens, one at a time); a lens' prompt carries the AV script and only what that lens may see, and nothing of this session's reasoning. Each returns a per-scene/timecode verdict (keep / rewrite / cut) with the reason:
   - **cold viewer** — the script + the first frame, no README: what is this, for whom, why should I care; the first frame must answer it with the sound off. Fails on "generic".
   - **skeptic** — every line against the footage and `evidence`: is the hook's promise kept, does the outro promise something the video contradicts, does it narrate the tooling (meta, filler, the same code twice, a path or a flag)? Written to be heard: short, one idea; identifiers only through `spec.say`, the real token stays in the captions (`phonetic_in_narration` is an error). The plan's own vocabulary ("booth loop", "sales beat") and research URLs stay in `direction.md`, never on screen.
   - **editor** — words/s per scene, three scenes in a row alike, a still plan over 5 s, text with no reading time, no pause where the topic changes.
   Consolidate into **one** list — must-change × preference, with timecode — and only then rewrite; `validate_spec` after. Max 2 cycles: if the cold viewer still fails, go back to the arc, not the sentence. Re-run the lenses after any rewrite that changes meaning.
4c. **Rounds.** Each gate states the one question of its round and what is **not** judged: round 1 structure (arc + hook), round 2 words (AV script), round 3 rhythm (rough cut — Fase 2), round 4 delivery (spelling, levels, formats, licences). One round, one question; a closed round is not re-litigated in the next, and its notes stay next to the spec.
5. **Rough cut before any capture (round 3 — stop here).** `narrate(spec_hash, scratch=true)` (same engine, same cache; the manifest is only labelled `"scratch": true` and the delivery `resolved_hash` does not move), then `animatic(spec_hash)` (a background job: poll `render_status`, the receipt has the MP4 and `pace_map`): every scene becomes a card with its visual-column placeholder and its own line, 360p/15 fps, `ANIMATIC` watermark, no music, MP4 outside `out/<resolved_hash>/`. Watch it and judge **structure only** — order, what each scene says, does the hook land, which beat is missing; its `pace_map` gives `dur_s`/`words`/`wps`/`lead_s`/`tail_s` per scene and a `caveat` you must repeat to the user: the synth is more regular than a human, so the pace is re-timed with the final voice. Then `shot_list(spec_hash)`: one row per capture with `hold_s` (the time the voice left after the line) and the `file:line` `evidence` it has to prove — capture **to that list**, not "whatever fits".
   Capture by kind — **always pass the chosen `aspect`**, it sets the viewport/cols/rows/screen size for that format.
   - web: start the app on the host, `capture_web` on `http://host.docker.internal:PORT` (`selector` gives a zoom `focus`, scrolled into view and clamped to the shot; `hide` blurs private areas; `goto_path` — alias `path` — is the route, `wait_for` a selector, `settle_ms` the paint settle). **Probe every route by URL before scripting** (`curl -s -o /dev/null -w '%{http_code}' "http://localhost:PORT/<path>"`): a SPA with no deep-link/server fallback answers 404 or re-renders the home, so it *cannot* be shot by URL — plan a recorded click-through with the [`screencapture`](../screencapture/) skill (`--record web`, steps) instead and say which scene holds the clip (the `image` scene with that `video`). Wait for the data (`wait_for`, `settle_ms`) so a skeleton is not what you capture, and look at each PNG/MP4 before claiming it is populated.
   - cli: prefer `capture_terminal_session` (real typing). Put `PATH`/`cd`/aliases in its `setup` so the prompt shows `mint_loader ./leak`, never `/repo/...`; keep a demo program in the repo or the image, not a typed heredoc (long, and "nothing typed" claims turn false). Otherwise: build first if README says so, then `capture_terminal` with the README commands. Max 16 lines; pick a short, meaningful run and size the window to it — `rows = printed lines + 1` (the 16-row default leaves ~44 % blank at 9 lines), or pass `crop_empty=true` to drop the blank rows under the last line (opt-in; the session take is re-encoded, `capture_terminal` just drops them). `capture_terminal` is the *text* path: it runs the command and renders a reconstructed `$ command` line plus the captured output as a styled block — no terminal, no keystrokes, so never present it as a screen recording. For motion, `capture_terminal_session`: steps of `type`/`key`/`wait_for`/`hold_s` record a real shell in a real xterm — **this is the only tool that captures real keystrokes and real screen output**; typing speed is staged but the output is real, so never type a result by hand; wait for it with `wait_for`, which matches **substrings** — wait on a unique token (never `active flow`: it also matches `no active flows`); `hold_s` is numeric: `{"type":"hold_s","s":2}`. (`regex: true` on `wait_for` is a `screencapture` host-recorder option, not for `capture_terminal_session`.) Its window defaults to the format's geometry (16:9: 80x16 at font 22, a wide short window that fills the content-box width at ~20 px glyphs; 9:16: 44x28 at 15), and the scene must keep the final output visible for about 4 s after typing ends: set `duration_s >= typing_end_s + 4` (the capture reports `typing_end_s`; `validate_spec` warns `short_hold` otherwise).
   - gui: `capture_gui` with `xterm -bg black -fg white -fa 'DejaVu Sans Mono' +sb -e '<cmd>; sleep 20'` for a terminal UI, or the app binary itself (the image ships no GTK/Qt, so a GTK/Qt app is host-only unless you build an image with its libs). A whole desktop screenshot is mostly empty: pick a screen `size` close to the app window and give the image scene a tight `focus`, or the zoom can only show a stamp in the dark. Always view the PNG; a blank or white shot means fix the command, do not ship.
   - code: `extract_code` for a ≤18-line snippet with its `file:line`.
6. Build the spec, `validate_spec` until no errors; keep `spec_hash`. Any spec change gives a new hash.
7. `stills` → look at every image (cropped text, blank, wrong theme) **and fix every layout warning it returns** (`outside_frame`, `safe_zone`, `clipped_content`, `focus_outside`, `container_path`): they are measured boxes, not opinions. `audit_layout` re-checks without the screenshots. Fix and repeat.
8. `render` (`draft` first, then `delivery`), poll `render_status`, then `verify` (it expects exactly 1920x1080, or 1080x1920 for 9:16). Report the MP4, SRT and poster paths from the work volume (`storyboard-video-work`). Asked for a voice-over? `narrate` **after** the stills are approved, `stills` again, then render: the audio lands in the MP4 and `verify` checks it (see Voice-over).
9. Want both formats? Do not squash one into the other: `reframe(spec_hash, "9:16")` clones the spec, applies the portrait rules (max 4 bullets, terminal lines ≤ ~40 cols) and lists the captures you must redo with the new geometry (it returns the exact parameters). Re-capture, put the new paths in the reframed spec, `validate_spec` again, then `stills` → `render` → `verify` per aspect. (Fase 5, ainda não disponível: `cutdown(spec_hash, target_s, placement)` trims a locked master to 15–30 s — today a shorter cut is a new spec, written by hand.)
10. **Cutdown and delivery.** A 15–30 s ad is a cut of the master, not a faster voice: `cutdown(spec_hash, 30)` removes whole scenes by arc role (implication, extra value, problem, tail; `hook`, `proof`, `result` and `cta` stay) and returns the new `spec_hash` with `removed`; `cutdown_infeasible` gives `min_s`, `hook_promise_unkept` means the cut would drop the proof of the hook's promise. It needs `direction.scenes` roles. Then re-run `narrate`, `stills` and the gates on the cut. Each review round: `round_log(n, question, notes=[{timecode, severity: must|pref, text}], decision, hash_before, hash_after)` writes `/work/rounds/<n>.md`. Ship with `deliver(spec_hash, project, aspect, version, date)`: it checks SRT, `CREDITS.txt` and licences, names the file `<project>_vNN_<16x9|9x16>_<date>.mp4`, archives the older ones and repoints `deliveries/CURRENT`.

## Spec
```json
{"fps":30,"aspect":"16:9","lang":"pt-BR","music":{"path":"/music/<id>.mp3","start_s":3.2,"title":"…","creator":"…","license":"CC BY 4.0","license_url":"https://creativecommons.org/licenses/by/4.0/","source_url":"…","attribution":"…","volume_db":-18,"duck":12},"theme":{"bg":"#0f1115","fg":"#f2f4f8","accent":"#4cc2ff"},"motion":"subtle",
 "direction":{"purpose":"feature-demo","tone":"calm technical","palette":{"bg":"#0f1115","fg":"#f2f4f8","accent":"#4cc2ff"},"palette_source":"user","audio":"voice","pacing":{"max_words_card":6},"brief":{"audience":"…","pain":"…","promise":"…","cta":"…","placement":"hero"},"arc":"hero","research":[{"url":"…","take":"…"}],"must_avoid":["thanks for watching"],
  "scenes":{"hook":{"role":"hook","text":"…","align":"center","narration":true},"why":{"role":"problem","narration":true},"cta":{"role":"cta","narration":true}}},
 "scenes":[{"id":"hook","type":"title","title":"…","subtitle":"…","duration_s":3,"caption":"…"},
  {"id":"why","type":"bullets","heading":"…","items":["…"],"evidence":"README.md:5","duration_s":4},
  {"id":"run","type":"terminal","heading":"…","lines":["$ cmd","out"],"duration_s":5},
  {"id":"live","type":"terminal","video":"/work/captures/<id>/session.mp4","poster":"/work/captures/<id>/poster.png","title":"mint_loader","heading":"…","duration_s":5},
  {"id":"ui","type":"image","image":"/work/captures/<id>/x.png","focus":{"x":0,"y":0,"w":0.5,"h":0.4},"zoom":1.6,"duration_s":4},
  {"id":"src","type":"code","code":"…","source":"src/a.c:1-12","duration_s":4},
  {"id":"cta","type":"title","title":"…","subtitle":"…","duration_s":3,"caption":"…"}]}
```
Types: title, bullets (≤5, ≤4 in 9:16), terminal (≤18 `lines`, or a recorded `video`+`poster` shown in a window frame), image (`focus` + `zoom`): the capture covers the frame and the focus is centred, with the pan and the zoom clamped so the focus stays in shot; give it a `video` (mp4, webm or gif, e.g. from the host [`screencapture`](../screencapture/) skill: `--record web|term|gui --format 16:9|9:16` with scripted clicks/keys; the format must match the video's aspect, as with the capture tools; clips have no audio, and the recipe `.json` is a record of the take, not a scene field) instead of `image` for a moving clip, same cover and zoom, code (≤18 lines). `duration_s` runs **1.5–12 s** per scene — a longer clip is split across scenes. Text ≤18 words per element (or `direction.pacing.max_words_card`); a caption or bullet is a callout, ≤8 words (`callout_too_long` warns), and on-screen text is read at ≤3.2 words/s. A near-empty capture gets a `sparse_capture` warning — re-run it, don't ship a blank screen.

`direction` is the director's brief and the only place the look is decided; every field has a reader, and `validate_spec` rejects a bad type, enum, palette or plan: `audio.target_lufs` (spec-level, −24..−12, default −14), `purpose`, `tone`, `palette` (+`palette_source`: `user` makes a contrast miss a warning, not an error) into `theme` (an explicit `spec.theme` still wins), `motion` (`still` never moves, `subtle` = the default 0.8 s settle then hold, `lively` = the old continuous scale), `audio` (`voice|music|silent`), `pacing.max_words_card`, `research` (`[{url, take}]`, host-side only), `must_avoid` (`validate_spec` warns when a phrase lands on screen), and `scenes` = `{<scene id>: {role, text, align, narration}}` with `role` ∈ hook|problem|implication|reveal|value|proof|result|cta and `align` ∈ left|center. `brief` (`{audience, pain, promise, cta, placement}`, from the **Brief** step) and `arc` (`ad|hero|walkthrough|booth-loop`) are Fase-1 fields: `validate_spec` type-checks them, an unknown `arc` only warns, and a server older than Fase 1 ignores them — they never block a render. `no_direction` is a warning on an older spec; `no_role`/`scene_unused` warn when the plan lags the timeline; `narration_off_plan` errors when a scene speaks against a `narration:false` plan.

## Done when
`verify` returns `ok`, you reviewed the stills, the layout audit reports no warnings, every captured asset matches the delivery aspect, and every number or claim traces to a capture or `file:line`. The video obeys its direction: the palette is the one the user approved, the scenes are quiet where the plan says visual-only, and the text settles instead of growing for the whole scene (one scene shot with `stills(spec_hash, at_s=1.5)` and again at `at_s=2.5` gives the same `digest`). With narration, `verify` also reports the `audio` stream (codec/duration) and errors when the voice-over is missing or its duration differs from the picture by more than 0.1 s. When `spec.music` has a `path` the render mixes that bed under the voice, ducked, and normalises the whole soundtrack to **-14 LUFS** (web default; `spec.audio.target_lufs` -24..-12 overrides; AAC 192k, true peak under -1.0 dBTP); `verify` reports the measured `loudness` (`integrated_lufs`, `lra_lu`, `true_peak_db`), `silences` and the track's `music_license`, and errors on a miss, on more than 3 s of silence in a narrated video, or with `credits_missing` when the credit block never reached `/work/CREDITS.txt` or `out/<resolved_hash>/CREDITS.txt`. A narrated spec rendered without its voice-over (bed only) is `no_voice`, not ok. With narration, the delivered MP4 is transcribed with the `faster-whisper` MCP and the **WER against the script is ≤ 0.15 and reported**; if that MCP is unavailable, say so explicitly instead of skipping the check silently. And `say_missing` is zero: every acronym that is spoken has a `spec.say` entry (`API` → `a p i`).

## Voice-over
Only when the user asked for narration. Both plugin entries keep `/tmp` writable and **exec** (`--tmpfs /tmp:rw,exec`; the previous engine's G2P `dlopen`ed from it, Pocket TTS only writes a temp WAV there). The engine is a CPU-only binary with the weights baked in: no network, no speed control — **the voice sets the pace and the expressiveness**. `spec.lang` (`pt-BR`|`en`) is required for it, and every spoken line is `scene.narration` (a sentence or two, written to be *heard*, not read: no `--flags`, no identifiers).
0. **Pick the voice.** `pt-BR` has a single voice (`rafael`, the only native speaker): do not ask, use it. For `en`, only when there is narration and the spec has no `voice`: ask the user three short questions — pitch (deeper / higher / no preference), emotion (calm / neutral / expressive) and pace (slow / normal / fast); add flow (smooth / breathy) only if they care. Then `suggest_voices(lang, pitch, emotion, pace, flow)` and offer the top 3 with their measured numbers (it also says which need CC BY attribution). Set `spec.voice` to the choice; the default is `rafael` (pt-BR) / `george` (en). Naturalness and accent are **not** measured: say so, and let the user hear a pick via `narrate(scratch=true)` before committing. `speed` is not supported (`speed_unsupported` blocks it); an old voice name (`pf_dora`, `af_heart`) is `bad_voice`.
1. `validate_spec` — `missing_lang` / `bad_lang` block; `narration_pace` warns when a scene has more than ~3.2 words/s of speech; a spoken number still needs `scene.evidence`.
2. `spec.say = {"LD_PRELOAD": "el di preload"}` spells anything the engine would mangle. Pocket TTS has no G2P to tune: in pt-BR an English word inside a Portuguese line is read with Portuguese rules (measured: "offline" came out as "Flini" with `rafael`), so map every English term to its spoken-in-Portuguese spelling (`"offline": "óflaine"`) and re-listen. `say_missing` warns for every acronym, snake_case/camelCase token and every on-screen identifier you speak, so add a mapping for each — never let the engine invent a pronunciation. Keep the spoken form out of `scene.narration`: the captions are cut from the narration, so `validate_spec` errors with `phonetic_in_narration` when a `say` value leaked into the spoken line (`container_path` warns when on-screen text shows `/work`, `/repo` or `/tmp`).
3. `narrate(spec_hash)` writes one WAV per scene to `/work/audio/<spec_hash>/` and a manifest with the measured durations; re-running is cached per line. A scene now lasts `max(duration_s, audio + 0.4 s)`.
4. Re-run `stills` after `narrate`: the resolved spec changed, and a delivery render is refused until you review the new stills. Only narrate **after** the stills are approved, so you do not pay for speech you then re-cut.
5. `render` muxes the voice-over into the MP4 (each scene's WAV at that scene's start offset, AAC) and writes the SRT from the narration, cued by the measured manifest duration. `verify` must report `audio` (codec, duration within 0.1 s of the picture) and `ok`.
   **Cues (Fase 3, estimated sync).** `scene.cues = [{"on": "phrase said once", "item": 1, "lead_ms": 120}]` on a `bullets`/`terminal` scene makes item `item` appear when the voice reaches `on` (`narrate` stores estimated `words` + `align: "estimated"` in the manifest). Pocket TTS has no timestamps: phrase boundaries come from the real pauses in the WAV and words inside a phrase are weighted by syllables, so expect on the order of 100–200 ms of error (measured on the previous engine, not re-measured) — land a reveal on a phrase, never promise word-exact sync. `cue_unmatched` (warn) = phrase missing or said twice, the item keeps its fixed delay; `bad_cue` (error) = malformed. `STORYBOARD_CUES=0` turns cues off; a spec without cues renders as before. Also per scene: `pause_after_s` (0–2 s) holds the scene that long after its line, and `audio_lead_s` (0–0.4 s, J/L-cut) starts the voice before the picture cuts to the scene, never over the previous line; `bad_pause` (error) = out of range. **SFX (Fase 4).** `scene.sfx = [{"at": 1.2, "kind": "tick|pop|hit|whoosh", "gain_db": -14}]` (`at` = seconds from the scene start) mixes a procedural effect (ffmpeg-generated, seeded, nothing to credit) after the duck, so it neither ducks the bed nor triggers it; it needs a voice or a bed to sit on. `audio.sfx:false` mutes all; `bad_sfx` (error), `sfx_density` (warn, more than 1 per 2 s). `verify` reports `duck_margin_db` (voice over the ducked bed, want ≥ 8 dB; `duck_margin` warns). `at: "cue:N"` plays at the moment the voice says `scene.cues[N].on` (unresolved ⇒ silent, `sfx_cue_unmatched` warn). A library effect from `music-search --kind sfx` uses `path` (`/sfx/<id>.mp3`) plus its `license` (CC0/PD only: `sfx_license_incompatible`, `sfx_path_missing` are errors) and lands in `CREDITS.txt`. `mkdir -p ~/.cache/storyboard-video/sfx` before the first session (docker would create it root-owned).
6. **Check what the video actually says.** Transcribe the delivered MP4 with the `faster-whisper` MCP (`transcribe(audio_path=<the MP4>, language=spec.lang)`) and compare the transcript to your `scene.narration` lines word by word. A dropped last syllable, a mispronounced identifier or a wrong number means fix the line/`say` mapping and re-narrate — do not ship a video you have not heard. Score it (WER on accent-stripped tokens) against a ceiling of **~0.15**: above that the line or the `say` mapping is wrong. Judge with the `small` model (the faster-whisper image default, `WHISPER_MODEL=small`); `tiny` misreads enough to make the score meaningless.

## Music
Optional, and **silent by default**: the image bundles no music. **The voice comes first, the bed after it**: pick the track only once `narrate` has fixed the durations (step 6 above, voice checked), because `fetch --duration` needs the real total and the cadence of the read decides the vibe — a bed chosen before the voice forces a re-cut. So the order is: lock the voice → `music-search` with that total → `spec.music` → one more `stills` pass (the hash changed with the music) → `render`. A `spec.music` on a spec with no `narrate` is music before the voice. (Fase 4 adds the `music_before_voice` warning for it; until then this order is discipline, not a lint.) When the brief answered with a vibe, use the [`skills/music-search`](../music-search/) skill (host, network):

1. `python3 skills/music-search/scripts/music_search.py search --vibe "<vibe>"` → candidates already filtered by licence verdict (allow: CC0/PDM; attribution: CC BY 4.0).
2. `… fetch <candidate-id> --duration <video seconds>` → verifies the licence at the origin, downloads, gates the audio, picks the window and stages the file in `${XDG_CACHE_HOME:-~/.cache}/storyboard-video/music`, which both plugin entries mount read-only at `/music`. Staging honours XDG but the mount is pinned to `$HOME/.cache`, so with `XDG_CACHE_HOME` set the file lands where `/music` cannot see it: `fetch` then returns a `mount_hint` — restage with `--stage-dir "$HOME/.cache/storyboard-video/music"`. Otherwise there is **no copy step**: the path just works.
3. Put its JSON into `spec.music`: `{"path": "/music/<id>.mp3", "start_s": 3.2, "title", "creator", "license", "license_url", "source_url", "attribution", "volume_db": -18, "duck": 12}`. `volume_db` is the bed level (about -18 dB, never above -6) and `duck` is how far it drops under narration (roughly 7 dB at the default 12 — a direction, not a dB scale).

`validate_spec` errors on `music_path_missing` (not a file under `/music`, `/work` or `/repo`), `music_license_missing` (no licence, a **CC BY** track with an empty `attribution` or no licence link, or a licence string it does not recognise: the gate is an allow-list — CC0, public domain, CC BY — and fails closed), `music_license_incompatible` (NC/ND/SA: a promo is commercial and syncing is an adaptation), `bad_music_start` (`start_s` is not a number ≥ 0) and out-of-range levels. The render writes the credit block to `/work/CREDITS.txt` and to `out/<resolved_hash>/CREDITS.txt` next to the video, and `verify` errors `credits_missing` when neither carries the track — **CC BY means the credit is a licence condition**: hand the file's lines to the user for the video description (CC BY 4.0 §3(a): creator, title, licence name + link, source, and the `Changes:` line).

No candidate for the vibe → report "no results" with the skill's `reason` and render **without** music. Never substitute a track you did not licence-check, and never present a track as claim-proof: **Content ID risk is unmitigated** (no Pixabay/Mixkit catalogue behind `/music`), so keep the sidecar `music-search` wrote next to the audio (`license_evidence`, `source_url`, `sha256`) for a dispute.
